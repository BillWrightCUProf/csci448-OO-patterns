In this homework you'll start to use Behavior Driven Development (BDD). These are tests that are
written in a human-readable language, called Gherkin, that describe the behavior of the program.
An example of a BDD test is shown below:

```gherkin
  Scenario: Play the simplest game
Given a maze with the following attributes:
| number of rooms       | 1 |
| number of adventurers | 1 |
| number of creatures   | 1 |
When the game is played in the created maze
Then all the adventurers or all of the creatures have died
```

A scenario is an individual test case. It is located in a feature file (with an extension of '.feature') that is
located in the src/test/resources/features directory. In that directory, we could put any number of feature files,
each describing a particular feature.

An individual scenario is composed of a number of steps. Each step starts with a keyword
that describes the action to be taken. The keywords are:

* Given
* When
* Then
* And

The keywords just mark the beginning of a step. The rest of the step is written in the natural language. The actual
keyword is not important, but you should select one that best describes the action and reads the most naturally. The
rest of the step is used to find the corresponding method in the code. This is done via annotations. A step with
no arguments or variability easily maps. In the scenario above, this step:

```gherkin
    When the game is played in the created maze
```

Would map to the following method:

```java

@When("the game is played in the created maze")
public void theGameIsPlayedInTheCreatedMaze() {
    // Write code here that turns the phrase above into concrete actions
}
```

This is a simple, direct mapping of the step text. Note that the method name does not matter when it comes to mapping
a step to a method. The only thing that matters is the text in the annotation.
Of course, you are required to use a good name for the method and the one generated by Cucumber
is generally good enough.

For a step like this:

```gherkin
    Given an adventurer "Bilbo" with health 5.0
```

We could map it directly to the following method:

```java

@Given("an adventurer \"Bilbo\" with health 5.0")
public void anAdventurerNamedBilboWithHealthOf5() {
    // Write code here that turns the phrase above into concrete actions
}
```

But it is much more powerful and useful to map it to a method that takes two arguments:

```java

@Given("an adventurer {string} with health {float}")
public void anAdventurerWithHealth(String name, float initialHealth) {
    // Write code here that turns the phrase above into concrete actions
}
```

This way we can reuse this step in multiple scenarios with different values for the name of the adventurer and the
initial health of the adventurer.

When defining a step definition, you can use the @Given, @When, @Then, @And annotations. It doesn't matter which
one you choose, as it will match any keyword in the feature file.

You need to write the missing steps in the feature file. These steps are currently in three different step definition
classes (PolymorphiaStepDefs, MazeStepDefs, and CharacterStepDefs). You can add more step definition
classes if you want. Notice that
you can inject a step definition class into another step definition class just by specifying it as a required
argument in the constructor. CucumberJVM, the framework we use to run the tests, will automatically instantiate
the step definition classes and inject them into the other step definition classes. It does this using a
Dependency Injection framework called Picocontainer.

You will need to create some instance variables in the step definition classes to hold
the objects created in one step that you'll need in another step.

To run all the BDD tests, you can right-click on the src/test/resources/features directory and select Run Tests
as we normally do.

## Additional Maze Construction

Notice that one of the steps in the feature file is:

```gherkin
    Given a maze with the following attributes:
| number of rooms       | 1 |
| number of adventurers | 1 |
| number of creatures   | 1 |
```

This will require you to write a method (a test method, for now) that can create a maze with an arbitrary number
of rooms, adventurers, and creatures. You can choose to connect the rooms in any manner that you like, provided
that all the rooms are connected together in some fashion, meaning it is possible to move from one room to any other
room, though you might have to traverse many rooms to do that.

You might need to add methods to existing classes to make this work. If you do, strive
for encapsulation as much as possible.

You will have to change at least one method: the _fight()_ method in the Character class.
